# 修复状态切换期间的画面丢失

已部署到 `http://192.168.2.16:8088/`。本次修复视频连续性，不调整模型、检测阈值、工时或计数规则。

## 复现与原因

原页面只要一次相机响应出现 `preview_fresh=false`，就调用 `resetStream()` 清空视频并重新建连。在测试浏览器中注入一次这种响应，实际记录到 1 次“Preparing video”遮挡、1 次额外 WHEP 请求，视频轨道发生变化。开工附近的后端观测记录没有超过 1 秒的中断，不能把这个现象归因于模型停止检测。

还发现同类路径：任意业务状态请求失败会清空播放器；连续相机状态超时，即使视频仍在正常解码，也会清空画面；任何配置版本变化都会重连；视频心跳一次网络错误或服务端错误会立即降级；后端在帧短暂过期时立即销毁编码器和会话；备用 MJPEG 缓存清空时直接断流；清零时间会连带使相机媒体失效。操作后刷新还可能额外启动独立轮询链。

## 已实施

- 用相机流身份、媒体 epoch 和隐私策略管理视频生命周期。开工、在岗、暂离、休息、完工与业务会话 ID 不作为重连依据。
- 区分“检测/操作是否就绪”和“当前视频是否仍在正常播放”。状态接口缺失时，实际解码帧仍更新就保留视频，统计显示待同步、相关操作禁用；没有新帧时仅保留有限恢复窗口。
- 状态请求分别处理成功或失败；轮询串行，操作刷新复用正在执行的一批请求。
- 心跳的短时网络错误、5xx 或一次统计读取失败不再丢弃正常 RTP。失效会话和持续无帧仍恢复连接，旧连接异步返回的统计不会影响新连接。
- 后端立即停止发布过期像素并清除 JPEG 缓存，同一媒体 epoch 内额外保留会话和编码器 5 秒等待新帧。持续过期、断线或策略失效仍回收。MJPEG 在缓存短暂清空时等待下一张新图。
- 清零时间仍结算历史并清空业务观测，但保留相机视频连接。隐私、训练模式、摄像头更换和需要重新处理画面的设置仍使旧媒体失效。

| 持续无帧、失效会话、隐私错误、训练模式、真实离线状态 | 自动检查确认触发失效/恢复，不把旧帧当作有效检测数据 |
| 后端短暂停顿及恢复、过期 JPEG 清空及恢复 | 自动检查确认原编码器/连接被保留、过期帧没有发布；持续停顿释放资源 |
| 清零时间 | 自动检查确认保留媒体连接且历史结算与重复请求处理仍正确；未在生产主动清零用户会话 |

状态投影及故障注入只替换专用测试浏览器中的读取响应，不修改生产工时或计数。后续已移除替换，现场视频保持真实输入。此次没有拔摄像头或改变现场隐私配置，相关边界通过回归检查验证。
